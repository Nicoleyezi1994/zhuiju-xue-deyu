# 追剧学德语新一集学习数据制作流程

这份技能封装了"追剧学德语"播放器每做一集学习数据时应该走的完整流程。目的是保证质量（尤其是翻译对齐这种容易出大错的环节）和格式跟已有各集保持一致。这个播放器可以配合任何一部你自己在追、语速正常、字幕齐全的目标语言剧集使用。

播放器本身是单文件网页（`index.html` + `manifest.js` + `data/<episode-id>.js`），不需要构建工具，双击打开浏览器直接用。这个 Skill 只负责"新一集的数据文件怎么做"，不负责改播放器引擎代码（引擎一般不用改）。

## 前提：需要哪些文件

开始前，确认已经拿到（或让用户提供）：

- 新一集的 `.srt` 字幕文件。
- 确认这台机器上 Python 命令叫什么：下面所有命令都用 `python3` 举例（macOS/Linux 通常如此）。如果用户在 Windows 上、用的是 python.org 官方安装包，命令通常叫 `python` 而不是 `python3`；不确定就两个都试一下。
- 已有集数的文件夹结构作为格式参考，通常长这样：

```
（项目根目录）/
  index.html
  manifest.js                 <- 剧集清单，做完新一集要在这里加一行
  data/
    s01e01.js, s01e02.js, ...   <- 已完成的剧集数据，可当格式参考
  tools/
    parse_srt.py                <- 通用 srt 解析器（不用改）
    check_dup.py                 <- 跨集生词/语法查重（可选，如果项目里有）
    check_highlight.py           <- 生词高亮触发校验（可选，如果项目里有）
    used_vocab_grammar.json      <- 跨集追踪表（可选，如果项目里有）
```

如果用户手头的项目文件比较旧、缺了某些工具脚本，就跳过对应的可选步骤，或者只用 `parse_srt.py` 这一个通用脚本重新开始。

## 第一步：解析 srt

把新一集的 `.srt` 复制到 `tools/` 文件夹，跑：

```bash
python3 tools/parse_srt.py tools/<episode-id>.srt tools/cues_<episode-id>.json
```

会输出总条数、纯音效条数、真正对话条数。这一步脚本是通用的，不用改代码。

## 第二步：确认真实的剧集标题（不要瞎猜）

**踩过的坑**：曾经把某一集标题猜成了剧中反复出现的核心概念词，但实际查证后发现标题完全不是那个词。

所以每做一集，必须查证真实的官方剧集标题（比如查权威的剧集数据库/Episodenguide 页面，或该剧的官方剧集列表），不要凭"这一集反复出现的关键词"去猜标题。查证前先问用户这部剧叫什么、季数集数是多少，不要假设。

## 第三步：逐句翻译（最容易出错的一步）

**血泪教训**：直接按顺序写翻译列表，容易因为剧中大量重复短句（比如某种重复性台词模式）导致翻译词典的书写顺序跟原文顺序对不上，造成大规模译文错位。

**正确做法**：

1. 先跑一个脚本，把所有"非纯音效、非空"的对话行连同它们的 idx 打印出来（参考 `cues_<episode-id>.json` 里 `sfx:false` 且 `text` 非空的条目）。
2. 新建 `tools/zh_<episode-id>.py`，写一个字典，**key 是 srt 里的 idx（整数），value 是译文**，不要按顺序写列表、也不要假设行号会一一对应——必须显式用 idx 做 key：

```python
ZH = {
  4: "译文……",
  5: "译文……",
  ...
}
```

3. 翻译完之后，必须跑一个校验脚本，确认：
   - "对话类 cue 的 idx 集合" 减去 "翻译词典的 key 集合" = 空集（没有漏翻的）。
   - "翻译词典的 key 集合" 减去 "对话类 cue 的 idx 集合" = 空集（没有翻错地方/多余的 key）。
   两边都为空，才说明对齐了。**这一步不能省**。
4. 翻译要注意该剧特有的双关、俗语或其他语言风格；翻不出双关时，在 vocab 或 grammar 的 note 里另外解释，不用勉强塞进译文本身。
5. **字符串引号坑**：Python 字典的说明字段如果用双引号包裹整段文字，内部又想用英文直引号标注术语，会导致字符串提前闭合的语法错误。统一改用「」全角引号书写说明文字，彻底避免这个坑。
6. **idx 对齐之外，还要单独抽查所有超短句（≤2个词）的翻译内容是否正确**：idx 对齐只保证"每句都有翻译、没有漏译"，不保证"翻译内容跟这一句本身对应"。独立成句的超短 cue（比如一个感叹词、一个简单的"是"/"不是"）最容易在翻译时被按整段语义意译、内容被挪到相邻句子上（而不是逐句对齐）。做法：翻译完成后单独列出所有 ≤2 个词的 cue，逐条核对翻译是否就是这一句本身的意思。

## 第四步：挑选目标难度以上的生词/短语（vocab）

**如果项目里有 `tools/used_vocab_grammar.json`（跨集生词/语法追踪表），先看一遍**：里面记录了目前已完成各集精讲过的所有生词（含所有词形变化）和语法点。挑到候选生词后，如果有 `tools/check_dup.py`，用 `python3 tools/check_dup.py 候选词1 候选词2 ...` 查一下有没有命中；没有这个脚本就直接打开 json 文件人工搜索候选词的词根。命中说明这个词根前面已经精讲过，**不要再作为新一集的新生词列入**，除非它在本集出现了全新的、值得单独讲的搭配或语法用法（这种情况要在 note 里写清楚"新在哪里"，不能只是换个例句重复同一个意思）。目标是全系列各集里，同一个词根只被精讲一次，把生词名额留给真正没学过的新词。如果项目里还没有这个追踪表，跳过这一步，正常挑词即可（追踪表是可选的加分项，不是每个项目都有）。

**选词方向（重要）**：优先选**日常高频、脱离剧情也能在任何场合用得上**的词和句型，而不是纯粹因为剧情/职业设定（法律、犯罪、医疗等）才出现的窄专业术语或粗俗俚语。判断标准：这个词换到一个完全不相关的日常场景里，是否照样常用？如果只在这部剧的特定职业/圈子语境里才用得上，优先级要降低，除非它本身高频常见或构词法很有教学价值。粗俗俚语只在确实是日常口语高频说法时才收，不要为了搞笑而收生僻脏话。

**第二条校准（同样重要，不要顾此失彼）**："日常高频"不等于"简单基础"。学习者要求的是超出初学者水平的词，不是任何入门阶段早就学过的基础词。选词要同时满足：①不是剧情专属的窄术语/黑话（上一条），②真的达到目标难度、要求学习者掌握某个不那么显而易见的义项/搭配/语域才能真正用对。"常用"和"简单"是两个独立的维度，一个词可以很常用但也很简单（要排除），也可以常用且有难度（这才是目标）。好例子：一词多义词（表面意思学习者认识，但某个引申义/固定搭配未必知道）、容易被学习者只知其一不知其二的副词、书面/口语都能用但需要专门学的话语连接词、生动但不能直译的习语。句子可以是口语常见的说法，但不要为了"日常"而故意选特别简单的句子/词，要保持真实的目标难度。

**第三条校准**："太简单"不只是最基础的入门词——一看就懂的国际同源词（和目标语言学习者的母语/通用语几乎一样），或者含义单一、没有任何隐藏难点的词（哪怕某些词表标了较高等级），同样算太简单。判断标准不是等级标签而是深度：这个词/搭配是否需要学习者已经知道某个不那么显而易见的义项/搭配/语域？如果看一眼就能从同源词或上下文猜出意思，或者只有一个显而易见的意思，大概率还是太简单。

目标数量：跟已有集数规模相当（一般 40-70 个左右，但如果这一集台词本身"日常通用+目标难度"双重达标的词不够，宁可少选、不要为了凑数硬塞剧情黑话或过于基础的词）。挑选标准：

- 优先挑**日常任何场合都能迁移使用**的词，哪怕例句来自这部剧的特定剧情。
- 复合词、俗语习语如果日常也常用，值得多讲讲构词法或双关义——这类词汇往往最有教学价值；但纯剧情/职业黑话要克制。
- 每个词需要字段：`id`(唯一标识)、`term`(词形)、`pos`(词性)、`level`(难度等级，如 CEFR)、`meaning_zh`(释义)、`example_de`(例句，**必须是 cue 里真实出现的句子，不要自己编**)、`example_zh`(对应译文)、`note`(词源/搭配/文化背景等)、`match`(数组，列出这个词在全集里出现的所有词形变化，用于自动高亮匹配)。
- **做完生词表后，如果项目里有 `tools/check_highlight.py`，跑一遍 `python3 tools/check_highlight.py <episode-id>` 核对每个词是否真的会被播放器高亮触发**。"example_de 的文本出现在某条 cue 里"不等于"真的会被高亮"——播放器按单词 token 逐个匹配 match 数组，所以连字符复合词、可分动词被拆开使用、match 短语中间被别的词隔开、无分隔符的长复合词，这几种情况文本检查会通过但高亮实际不触发。脚本列出的问题条目，要么在 match 数组里补上实际会出现的 token/短语，要么换一个真正包含该词的 cue 做例句。如果项目里还没有这个脚本，跳过这一步（它是可选的加分校验，不是每个项目都有）。
- 说明文字里如果要打中文引号，用「」全角书写，不要用英文直引号 " "。

## 第五步：语法点（grammar，8-10 个左右）

**选点方向同样偏日常通用**：优先选换成任何一个不相关的日常场景例句依然成立、依然有用的语法结构（比如委婉间接问句、被动态的区分、属格介词、可分动词+zu不定式语序、反身动词+zu不定式、方向小品词+介词搭配、口语省略句、固定副词短语等——具体清单取决于目标语言），而不是专门为了解释这部剧特有的职业/黑话语境才存在的语法点。

**同样先看 `tools/used_vocab_grammar.json` 里的 `grammar_topics` 列表（如果存在）**：如果候选语法点的主题（比如被动态、虚拟式、反身动词、关系从句、不定式结构这些几乎每集都会自然出现的基础结构）在前面某集已经完整精讲过、这次只是换个例句重复同一个讲解角度，就**不要再单独列为本集的语法点**——换成一个前面没覆盖过的具体子结构或更细分的用法。如果同一大主题下确实出现了全新的、值得单独强调的子用法，可以再选一次，但 `explain_zh` 里要写清楚这次和之前讲的角度有什么不同，不能是简单重复。

每条包含：`id`、`title`(语法点名称)、`tag`(简短分类标签)、`cue_idx`(对应的 srt cue 编号)、`explain_zh`(讲解)、`example_de`/`example_zh`(例句，同样必须来自真实 cue)。

**每一条选完之后，务必用脚本核对 `cue_idx` 对应的 cue 文本，是否真的包含 `example_de` 里引用的那句话**——这是最容易出错、也最容易被忽略核对的一步，之前吃过语法点指向不相关句子的亏。做新一集时这一步不能省。

## 第六步：总结（summary）、关键片段（keyScenes）、练习题（quiz）

- `summary`：`synopsis_zh`(整集简介，几句话) + `key_phrases`(6-8 个本集最值得记住的短语/俗语，`{de, zh}` 格式)。**`key_phrases` 要挑真正有语言学习价值的固定短语/习语/句式**，不要为了凑够数量而塞进剧情上重要但语言上平淡普通的句子（那种句子交给 keyScenes 的 note_zh 或 synopsis_zh 交代剧情就够了）。判断标准和选 vocab 一样：这句话是不是有固定搭配、习语、或值得专门学的句式，而不只是"剧情上很关键的一句话"。另外：`key_phrases` 里的每一条必须是**真正的多词短语/固定搭配**，不能是一个孤零零的单词——哪怕这个词已经在 `VOCAB` 里精讲过也不行。一个短语同时出现在 `VOCAB` 和 `key_phrases` 里是可以的，只要它本身是多词的固定搭配，问题只出在"塞进一个单独的词"这种情况。
- `keyScenes`：6-8 个值得回放的片段，每个包含 `start`/`end`(毫秒，**必须是真实 cue 的 start/end，从 cues 文件里查**)、`title`、`note_zh`。**`note_zh` 不能只写剧情摘要，必须点出这段值得回放的语言学习理由**：语速快还是慢、正式register还是口语、密度高不高、适合精听/跟读/练习哪类词汇或句型、适合初学者还是进阶者。**`title` 已经承担了"讲了什么剧情"的功能，`note_zh` 不必再复述剧情细节**——几乎全部篇幅都用来讲语言特征，剧情最多几个字带过。目标长度控制在较短的篇幅（比如 25-40 字左右），不要写成纯剧情总结，也不要为了兼顾剧情把整条写得很长。
- `quiz`：8-10 道题，**只留 1-2 道剧情理解题，其余大多数（6-8道）要针对本集选的生词/语法点做考查和运用**，不要几乎全是剧情问答。题型：
  - `type="mc"`：选择题，字段 `q`(问题)、`options`(4 个选项数组)、`answer`(正确选项下标，从 0 开始)、`expl`(解析)。**以这个题型为主**，适合考查习语/语法点的理解。
  - `type="fill"`：填空题，字段 `q`(题目，用___表示空)、`answer_text`(正确答案)、`expl`(解析)。播放器按"用户输入是否包含这个答案字符串"判分（不区分大小写），提交后会明确标出"✓ 回答正确"或"✗ 回答错误，正确答案：xxx"（引擎已内置这个反馈，不用额外处理）。**每集大概留 2 道左右就够**，用在最适合考查具体词形/搭配/介词格支配的地方，其余用选择题。
    - **`q` 必须只留一个空、给出含义提示，不能只标注词性/语法类别**：只说"这是个动词"完全不够，学习者不知道该填哪个词——哪怕这个词是本集精讲过的生词也一样。要在括号里给出目标词/搭配的含义释义。固定搭配/俗语类填空同样要给含义提示，光给出搭配骨架不够。唯一例外是**纯语法变形题**（答案由题目给出的语法规则/转换本身推导得出，不依赖记住某个具体词或俗语）。
    - **`answer_text` 用"/"分隔的是"多个可以互相替代的同一个答案"（OR逻辑），不是"必须都填对的两部分"（AND逻辑）**：如果一道题的空格需要填两个不同的词，用"/"表达会导致用户只填对一个就被误判满分。遇到这种情况，要么只留一个空、把另一个词写进题干，要么拆成两道单独的填空题。
  - 出题思路优先考虑"这个词/语法点怎么才能让学习者自己写出来或选对含义"，而不是单纯的剧情问答。

## 第七步（如果项目有追踪表，不能省）：把本集新生词/语法追加进追踪表

本集数据定稿后，如果项目里有 `tools/used_vocab_grammar.json`，把新增的 vocab 和 grammar 条目追加进去（不要覆盖已有条目，只追加）。这样做下一集时追踪表才是最新的，才能保证跨集不重复。

## 第八步：合并、更新 manifest、测试

1. 把 CUES(带译文) + VOCAB + GRAMMAR + SUMMARY + KEY_SCENES + QUIZ 合并成一个字典，写成 `data/<episode-id>.js`，格式是：

```js
window.APP_DATA = {...一整个JSON...};
```

2. 在 `manifest.js` 里加一行登记这一集（记得上一行末尾要加逗号）。
3. 起一个 `python3 -m http.server` 测试，打开页面，检查：
   - 下拉框选项里出现新加的这一集，标题正确。
   - 切换过去后 `CURRENT_EPISODE.id`、`VOCAB.length`、`GRAMMAR.length` 等等符合预期。
   - 挑 1-2 个语法点/生词，检查高亮和翻译显示正常。
   - 语法点的 `cue_idx` 对应的文本核对无误。

## 第九步：交付/提交

把 `data/<episode-id>.js` 和更新后的 `manifest.js` 交给用户，简单说明这次新增了什么。如果项目有一份记录整体进度的文档，做完一集后应同步更新其中的"已完成"清单。

## 重要提醒

- **涉及具体剧集的字幕原文、翻译、生词释义、题目属于版权内容，不要把这些真实数据提交或发布到任何公开仓库、公开网页**；只应留在用户自己的私人项目文件夹里，最多私下分享给用户指定的人。这个 Skill 本身、以及播放器引擎代码不含任何具体剧集内容，可以公开；`data/*.js` 这类真实学习数据不可以。
- 每一步的核对脚本（idx 对齐校验、cue_idx 核对、跨集查重、生词高亮校验）都不能省略，这是保证质量的关键，过去的质量问题几乎都是因为跳过了某一步核对。
